## 前提の整理

### needs_update 1,689件は「滞留」ではなく「告示待ちの正常状態」

本ドキュメントは当初「滞留しているneeds_updateを解消する」という発想で書いていたが、これは誤った前提だった。

正しい現状認識：

- **大多数の自治体は5〜7月にかけて R8 告示する**。5月時点では未告示が標準。
- `migrate-2025-to-2026.js`（4/27実行）が R7値そのまま+caps改定+childcare新設のplaceholderを置いたのは、**告示前のサイトとして R7値を仮表示しておくため**であり、設計通りの挙動。
- 現在 verified の **37自治体は告示前の先行情報を能動的にハンティングした成果**（横浜の試算用紙PDF、秦野の公式試算ツール等、公式発表前から各種試算手段で値が読み取れたもの）。
- したがって「1,686件をどう変換するか」ではなく、**「告示が出始めたらどう速く取り込むか」+「告示前の先行情報をどう効率的に発掘するか」** が真の論点。

## 戦略：2軸構成

### 軸1：先行発掘（告示前にどれだけ取れるか）

5月の今、各自治体は告示前で公式ページが更新されていない。それでも値を取れるパスは限られている：

| 取得経路 | 例 | 特徴 |
|---|---|---|
| 公式試算用紙PDF（告示前リリース） | 平塚（200198494.pdf） | 告示の数日〜数週間前に公開されることがある |
| 外注の試算ツール | 秦野 等 | 委託先システムが告示前に先行で値を反映するケースがある |
| 議会資料・予算書 | 23区の保険料率改定議案 | 議決後・告示前に値が読める |
| 自治体広報誌・お知らせPDF | | 印刷物が先行することが多い |
| 県の運営協議会資料 | | 県単位で各自治体の料率をまとめて公表することがある |

**先行発掘を回すための仕組み**：

- [ ] **発掘パターンの記録**：verified化した自治体ごとに「どう見つけたか」を `meta.notes` または別ログに記載 → 翌年同じ自治体に同じ手段が使えるかを資産化
- [ ] **発掘ターゲット候補リスト**：人口規模・前年告示時期・自治体規模からハンティング優先度を付け、どこを先に攻めるか可視化
- [ ] **試算ツール委託先の横展開検知**：委託会社が複数自治体を抱えるケースがあるので、ベンダー横断で先行公開を検知できる可能性を調査
- [ ] **県運営協議会資料の定期チェック**：5月の県運営協議会で各自治体の料率がまとめて発表されることがある

### 軸2：告示反応速度（告示が出たら即verifiedにする）

5月後半〜7月にかけて告示ピーク。このとき重要なのは「即取り込み・即デプロイ」の体制。

**速度を上げる仕組み**：

- [ ] **告示検知パイプライン**：自治体公式の国保料率ページの「最終更新日」「ページタイトルの年度表記」を週次でチェックし、変更が見つかった自治体をダッシュボードに上げる
  - すでに `scripts/dashboard.js` がある → これを発展させる
- [ ] **値抽出のテンプレート化**：HTML/PDF/Excel から `rate.medical` 等を抽出するLLMプロンプト or 抽出スクリプトを定型化
- [ ] **取り込みワークフローのワンコマンド化**：「URLを投げると → 抽出 → kokuho-2026.json更新 → デプロイ」までを `node scripts/ingest-r8.js <slug> <url>` のような1コマンドに集約
- [ ] **県集約資料の年次取り込み**：北海道・茨城のように「県が市町村別保険料率一覧を出す」ケースは、出たタイミングで一気に20〜180自治体をverifiedできる。これは告示後の話なので、Phase 2 として位置づけ

## 期待効果

- 告示シーズンの取り込み速度が **手作業1自治体30分 → スクリプト化で数分** に短縮できれば、6月の告示ピーク（仮に1日50件告示）でも当日中に追従可能
- 県集約資料が出る県（10〜15県程度を見込む）は北海道・茨城パターンで一気に数十〜180件verified化可能
- 翌年度（R9）以降、今年蓄積した発掘ログを起点に攻略が高速化
